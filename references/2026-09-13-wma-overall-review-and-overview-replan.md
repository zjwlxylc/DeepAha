## 2. 新闭环与唯一人工决定

```mermaid
flowchart LR
    A[保存 WMA 原始结果] --> B[自动检查与生成备注]
    B --> C[完整总览预览]
    C --> D{整体决定}
    D -->|通过| E[内容与备注进入总览]
    D -->|不通过| F[保留返回与整体原因]
```

### 2.1 “通过”准确表示什么

- 审核单位是当前一份 WMA 返回的一个明确版本；包含的公告、子对象数量及有问题的内容在同一预览中可见。不自动扩大到其他返回或后续版本。
- **通过**表示“同意将本页范围的内容及所列备注纳入总览”；不表示逐字段真值核验、Gold、资格规则批准或个人可报名。
- **不通过**只需一个整体原因；用户不必先逐条纠错、补材料或解释程序内部状态。
- 正常及带备注的返回都只有这两个决定按钮。备注由程序汇总；用户可补充一条整体说明，不要求逐字段填写或逐项勾选。
- 不默认选中通过，不预填“本人已核对全部原件”之类超出实际责任的声明。不把一次总览确认拆成一串虚假的人工事实批准。
- 有明确内容使用范围和展示权限的环境，保存通过时同时生成总览版本及收录记录。环境范围在审核前说明；本地试用默认受控可见，已有公开发布权限的环境可在同一次决定中发布允许的内容，不再增加内容审批页。
- 本规划不授权将真实数据新发布到公网；对外发布权限不足时，在预览上说明本次为本地收录，不在点击通过后才冒出发布门。

### 2.2 程序检查的三种处理结果

下面是程序处理方式，不是增加三类人工审核决定。

| 处理方式 | 典型情况 | 展示与后续使用 |
| --- | --- | --- |
| 正常使用 | 内容可归属，来源支持相应表述；确定性转换确有依据 | 正常展示。程序只声明实际检查过的范围，例如“引用已定位”，不夸大为所有含义均已验证 |
| 保留并备注 | 新字段、新表达、不会转换、局部引用未定位、附件未读、非关键内容缺失、局部冲突 | 保留原文/返回内容及影响说明；其他内容可收录；相关计算受限 |
| 整体不可收录 | 无法确认这份结果对应什么对象、核心来源错配、整份返回无法安全解析，或关键原件完整性破坏导致结果不能可靠使用 | 原始结果留在内部记录，一次给出整体原因；不能被点成有效总览 |

附加规则：

1. 问题默认只影响所关联条目、子对象或材料。一个非关键附件损坏不自动否定整份可读公告；若损坏使全部内容的依据失效，才整体不可收录。
2. 已证实错误的值不再作为正常值展示或运算。冲突可并列来源；无法确定所属子对象的内容放在明确的“归属未确定”区域，不能硬套到某岗位。
3. 准入阻断代码形成有限、版本化清单，每条必须说明为何整份不能可靠使用。转换能力、方法未启用、规则缺失、资格覆盖不足不得加入此清单。
4. 超时、工作进程退出和依赖服务故障是技术处理状态，不写成用户“不通过”。可读结果保留；可选检查未完成形成备注，必要的安全读取未完成则说明具体失败并允许恢复。
5. 展示所需检查在整体决定前汇总，附所用版本。没有材料/版本/权限变化时复用结果，不在保存以后继续要求完成未展示的审核步骤。并发变化时保留说明并重新取得当前预览，不伪装为内容错误。

### 2.3 备注必须可理解且对使用有效

| 内容 | 合适的呈现 | 禁止的处理 |
| --- | --- | --- |
| 岗位类别“管理” | 直接展示“管理” | 要求解释成资格规则后才能收录 |
| “硕士研究生以上”等明确原文 | 展示原句；暂不能计算时，仅说明不能据此完成自动资格判断 | 让审核员回答“是否应保留未知” |
| 引用未定位 | “此项为 WMA 整理内容，尚未定位到原件” | 冒充“原文已经核实” |
| 两个截止日期冲突 | 展示两处日期、各自来源及冲突备注 | 默选其中一个生成倒计时或截止提醒 |
| 部分附件未读 | 明确列出未读材料及可能影响，保留已读内容 | 宣称已返回字段全部通过，所以材料完整 |

维护诊断与用户备注分开：堆栈、内部 ID、账号、内部原因说明不进入公开 API。公开备注描述内容问题及实际影响，不要求普通读者理解方法、候选或事实集。

总览采用与旧 Gold/逐字段核验记录不同的收录标签，例如拟新增 `OVERVIEW_ACCEPTED`，并解释为整体收录。V2 清单不直接塞进旧 `PublicCatalogEntry` 以规避完整性要求；在 P4 完成消费兼容前，旧个人批处理不能误读不完整的 V2 记录。

### 3.2 陌生字段、重复标签与稳定身份

- 内容唯一键使用 `source_record_key`：有生产者稳定 ID 时验证后使用；旧格式采用返回哈希、实体键、文件位置/出现序号。同标签多次出现均保留，不以标签去重。
- 同一快照重复导入必须复用条目；新版本只有可靠来源键一致时延续身份，否则保留新条目及差异，不凭文字相似度宣称是同一事实。
- 沿用 Opportunity/Version、OpportunityUnit 及既有别名/归并记录。正式机会关联只复用已确认关联或来源内确定的唯一身份键；新且可唯一识别的机会，在整体收录事务中登记稳定 ID，无须另设身份审批页。
- 不依据相同名称或 WMA 的树形展示自动合并正式机会。无法确定归属的子内容可留在父级并注明；连基本机会身份都无法可靠区分时整体不收录，不让用户被引入多页绑定向导。
- 复用 `POSITION / TRACK / PROGRAM_TIER / REGION_VARIANT / DEFAULT_SINGLETON`。表述区块不创建 Unit，单位/共同内容沿用已有分组身份；来源显示继承关系不等于已批准计算适用性。
- 无法完整填满旧主快照时，不用假日期、假 URL、假地点或假事实补齐。新内容版本关联稳定机会身份及可用的正式版本，原 WMA 内容保持为明确的展示来源；不能强制先构造完整 VerifiedFactSet。

### 3.3 状态与使用限制

- 区分“材料明示”“当前材料未找到说明”“尚未提取/无法读取”“相互冲突”“明确不适用”。缺字段只能说明当前提取没有，不能推断官方没说或不要求。
- “未说明”需带所检查的材料范围；“不适用”需有原文/可靠确定性依据。没有依据时保留未确定，无需让人工逐条补齐才能收录。
- 程序保存条目是否已定位、能否可靠规范化，以及是否允许用于类型化筛选、日期行动、资格计算等限制。限制由服务端根据证据和实际能力生成，客户端不能传一个 `verified=true` 覆盖。
- 只因程序不会规范化，不应把清楚原文变成业务未知；但未知资格、脚注和例外仍在现有 CoverageManifest 中有位置，不能因进入“其他说明”而被忽略。
- `received_at`、`reviewed_at`、`last_source_checked_at` 分开；读取缓存不刷新来源核验时间，也不宣传整份内容所有字段均已核实。

| 陌生字段：服务期、待遇、知识产权、组队、兑付限制 | 原标签、完整原文及来源保留；未知分区归“其他说明”，始终可达 | P1、P2、P3 |

| 同名字段、多个时间节点、不同地区/赛道范围 | 按稳定条目身份和目标区分，不能覆盖 | P2、P3 |
| 多单位公告、不同子对象 | 复用真实对象类型与分组，显示父级共同内容；不能跨对象错套 | P2 |
| 月份、时刻、多轮报名、滚动受理、招满即止 | 版本化时间节点，保留原文、精度、时区及对象；不制造日期或持续开放结论 | P3 |
| 未知发布时间、没有固定截止日 | V2 允许明确的缺失状态；接收时间不伪装成发布时间 | P3 |
| 线下/线上/混合办理、没有申请 URL | 显示真实方式及官方说明入口；不因缺在线链接消失 | P3 |
| 全国适用、线上活动、无固定场地 | 适用地区与实际地点分开；没有地点不推断全国 | P3 |
| 发布方、主办方、用人单位不同 | 角色分别呈现，缺失角色不猜；先完整原文，再做确定性结构化 | P2、P3 |
| 金额的币种、周期、上限、条件 | 保留“每年最高”等限定；不能把最高额当固定待遇或相加 | P3、P4 |
| 附件未读、图像不清、WMA 漏项 | 从已有材料清单及可靠检查结果生成覆盖备注；没有检测能力不能报完整 | P1、P2 |
| 更正、延期、撤回、附件替换 | 新版本和影响范围明确，旧值不与新值拼接，缓存/提醒同步失效 | P4 |
| 招聘、竞赛、政策内容重点不同 | 三种受控布局及通用回退；任何新增字段都可在详情找到 | P3 |
| 长正文、大量条目、移动端 | 分页、按需证据、稳定排序；全部已收录内容可达 | P3、P5 |

### 4.1 时间与呈现规则

- `milestones` 每个节点有稳定 ID、业务标题、目标、原文、来源、种类（定点/区间/滚动/待公布）、精度（日/月/时刻/无精确值）和时区。首版不要求自动理解全部时间短语：不能可靠拆解时显示原文。
- 卡片的“下一行动节点”仅从可确定的行动时间选取，不能拿考试或作品提交截止替代报名截止。不确定时间不做精确倒计时；“常年受理”“招满即止”使用原文及核验时间。
- 排序显式区分已知与不确定时间；未知排在已知之后，并以稳定 ID 打破并列。游标携带读版本，避免更新期间跨页重复或漏项。
- 招聘优先显示岗位/职责/条件/报名；竞赛显示赛道/组队/作品/赛程/奖励/权利；政策显示对象/支持/材料/办理/限制。模板只组织内容，不能改变机会类别和资格含义。

### 4.2 系统管理的必要性评估与最小开发范围（2026-09-14）

#### 4.2.1 决定：需要独立职责和入口，采用现有应用内的小模块

**需要建设最小系统管理模块。** 当前已有 WMA 配置、来源、任务恢复和历史查询的实际操作；旧控制台退役后，这些操作需要明确归属。上线后也必须能够判断服务是否正常、阻止错误任务继续运行、调整配置及追溯操作。仅删除冲突入口而不提供归属，会迫使维护者继续使用旧路线或直接修改数据库。

这里的独立指导航、权限和服务职责清楚：与机会总览、整体审核分开；仍在同一 Web/API/数据库中，复用现有业务服务。**不建立独立管理站点、微服务、第二套账号、任务队列或配置事实源。** 一人可以同时负责运营和审核，但一次管理操作不能自动批准内容。

| 选择 | 当前收益与代价 | 对上线的影响 | 判断 |
| --- | --- | --- | --- |
| 继续把配置、来源、运行放在各业务页面，其他靠 CLI | 少写页面，但旧业务退役后共享功能无处归属，权限及错误提示继续混入审核 | 维护者必须记住多处入口；容易误操作旧任务，不能消除已确认冲突 | 不采用作为长期安排；CLI 保留处理低频运维 |
| 同一应用中设置最小系统管理入口，复用服务 | 需要少量页面、授权整理和依赖迁出，可直接承接已有能力 | 页面及领域服务可复用到上线环境，只替换认证、密钥和运行宿主适配 | 采用 |
| 建通用管理平台，账号/角色编辑器、监控大屏、备份控制台一并开发 | 首次交付和维护成本大，当前没有相应规模与操作证据 | 平台自身也需安全、兼容和运维，反而扩大上线风险 | 不采用 |

无法凭静态代码给出可靠工时。控制工作量的方法是限定操作清单和复用出口，不以“将来可能需要”增加子系统。

#### 4.2.2 实现依据与不能误报的能力

- `api/investigation_runtime.py` 已有 WMA 配置、连接检查、工作进程状态和派发接口，适合迁出业务页面；配置保存与派发要求操作员，部分读取/检查的权限需重新按职责划分。
- `investigations/local_config.py` 保存版本化配置，依赖 `SecretProtector / DirectoryHardener`；`runtime.py` 使用本机文件心跳。可以复用逻辑，不把 Windows 文件存储假定为所有部署环境。
- `sources/registry.py`、`sources/cli.py` 已有来源清单与导入能力，`api/investigations.py` 有来源读取；并不等于已有可在线随意修改来源政策的完整后台。
- `review/auth.py` 及账号/会话表已有过期、撤销和角色检查，但解析入口当前限制为开发/测试的 fixture 模式；没有可直接宣布为生产可用的登录方案。
- `api/local_human_test.py::require_local_human_test` 明确限制 development 与 loopback；`api/investigation_runtime.py` 和 Worker 的保护不能通过改名或删判断绕开。
- `api/health.py` 当前 live/ready 返回固定 ok。管理页不能据此声称数据库、存储、WMA 全部健康；旧控制台写死的阶段状态/真人数量也不能作为实时管理数据。
- `human-test/data-management.tsx` 的清空按钮禁用。未开发的删除、备份、恢复界面不列为已有成果。

#### 4.2.3 四个页面范围与实际操作

| 页面 | 近期必须有的内容/动作 | 明确不做 | 所属任务 |
| --- | --- | --- | --- |
| `/manage`：运行与连接 | 显示环境、实际版本、数据库读取/存储访问检查结果、Worker 最后响应、WMA 配置状态；本地模式保存 WMA 连接并显式检查。失败分别显示，不把一个组件异常变成全页不可读 | 不因打开页面而发起调查/远程连接检查；不做模型选择器、监控大屏或 Web 服务器重启按钮 | P1 基础，P5 验证 |

WMA 模型继续由 WorkBuddy 后台配置；系统管理只管理连接及已发布 Agent 绑定，旧 Provider 模型配置不作为新日常入口复活。WMA 调查任务的创建仍是内容业务动作，管理页负责配置及恢复，不复制一个平行“理解公告”功能。

账号开通、停用、权限分配与会话撤销必须有可审计的安全操作方式，但首版可由受控命令或已有身份平台完成，不另写账号 CRUD 页面。备份、恢复、部署、服务重启、证书、集中告警使用宿主平台或运维命令；上线时必须能实际执行，不要求把它们做成 Web 按钮。用户隐私请求仍由已有领域能力/受控流程处理，不能用系统管理替代，也不在这里新建用户画像后台。

#### 4.2.4 权限、状态与故障边界

1. **查看总览、审核收录、维护系统是不同操作权限。** 普通读者无管理访问；审核者可读取完成判断所需的内容，不能修改密钥、来源配置或恢复远程任务。管理者不因维护权限自动获得收录批准权。
2. 复用现有账号/会话和服务授权机制。新权限只采用固定角色/操作映射，不做通用 RBAC 编辑器。当前 `LOCAL_TEST_OPERATOR` 只能在明确的本地模式映射为维护权限；上线不能用它加 development 环境变量伪装生产身份。角色/用途枚举如需扩展，使用显式契约和追加迁移，历史角色含义保持不变。
3. 管理写操作在服务端校验操作者、用途、目标版本和幂等键，记录动作及结果；重用已有配置修订、任务事件、决定记录。缺少记录的来源暂停/恢复补充最小操作回执，不建设独立审计平台。
4. 暂停采集只停止新派发，不能复用“撤销来源可信性”开关导致历史内容全部失效。在途任务是否取消是明确动作；来源确实不可信则按 P4 的受影响范围处理。密钥轮换、Worker 暂停不改变已存原文的真实性。
5. WMA 暂不可用或管理页故障，不影响已准备内容的阅读与整体收录；缺必要数据时只说明具体受影响动作。管理接口不得成为每次审核 GET/POST 必须全部通过的健康门。
6. 返回和日志不含明文密钥、会话令牌及不必要个人信息。用 Cookie 的管理写操作执行 CSRF/来源校验；列表使用服务端授权和分页，不能仅靠隐藏菜单。
7. 管理页面读取有限、只读的检测结果和超时状态；昂贵/有外部请求的检查显式触发或由既有后台调度完成。检测未知显示未知，不把硬编码 ok 或“存在文件”当作完整健康证明。

#### 4.2.5 文件、接口及旧路线冲突的解决

拟新增 `web/app/manage/{page.tsx,sources/page.tsx,tasks/page.tsx,history/page.tsx,actions.ts}`、`web/lib/system-management.ts`、`backend/src/deepaha/api/system_management.py`，只包装现有配置、来源和任务服务。API 前缀拟为 `/api/v1/manage`，包含 status、sources、tasks、history 读取及受限维护动作；不新增第二套任务数据模型。

后端授权依赖放在拟新增的 `backend/src/deepaha/management/auth.py`；配置、运行状态等环境实现以小型适配边界接入，优先复用当前已有 Protocol，不预先实现多家云或身份供应商。具体操作仍调用相应领域服务，禁止在管理路由中直接写业务表。

明确修改/迁出：`api/investigation_runtime.py`、`api/local_human_test.py` 的共享依赖、`review/auth.py` 的认证适配、`investigations/local_config.py` 与 `runtime.py` 的宿主依赖、`web/components/investigations/runtime-panel.tsx`、`web/app/review/assurance/sources/page.tsx` 的旧控制台链接，以及启动器配置。`provider_config.py` 的通用密钥保护能力迁到中性模块或保留兼容导出，不能连同旧 Provider 业务一并删除。

`web/lib/local-human-test.ts` 当前固定旧 Cookie/请求路径；需将可复用的已认证请求逻辑迁到拟新增 `web/lib/reviewer-request.ts`，由新管理和整体收录分别调用自身 API。保留旧只读历史适配，不把改 URL 前缀当作已经解决认证。状态读取复用查询，不绕过来源数据本身的权限和范围。

冲突处理规则：

- 不再在审核页面嵌入连接配置、方法启用和维护长表单；只显示当前内容的必要状态，维护者有单独入口。
- 新管理页调用中性授权/服务接口，不靠删除 loopback 限制来继续调用旧测试接口；旧测试路由仍按 1.4 节退役。
- `/review/human-test` 的历史深链转到只读历史，来源入口转到 `/manage/sources`；旧写接口被明确关闭，不能借管理迁移悄悄恢复旧提取路线。
- 任务恢复继承原执行意图、预算、版本及外部调用限制，不把没有远程执行证据的失败自动重发为新调查。

#### 4.2.6 上线后需要什么，哪些现在不开发

最小管理职责上线后仍然需要，但页面形态不是全部运维能力。上线时沿用这四类操作及其领域服务，按实际部署宿主替换以下边界；不能因已有本地页面就声称已完成生产管理。

| 事项 | 本次 P1–P5 要做到 | 首次相应上线前必须做到 |
| --- | --- | --- |
| 登录与管理隔离 | 复用真实本地操作者记录，明确 fixture 只用于开发/隔离测试；业务服务不绑定具体登录来源 | 接入部署选择的真实身份入口/受保护访问，验证会话到期、撤销、角色越权和写操作保护；禁止公网暴露测试登录 |
| 密钥与配置 | 保持现有本地加密，抽出已有环境依赖；页面不读回秘密 | 若部署 Linux/容器，接入宿主秘密存储/受保护注入；不得复制 Windows DPAPI 密文当作可移植凭据。托管秘密模式下配置通过部署工具更新，页面可仅查看状态 |
| Worker、原件存储与任务恢复 | 明确任务状态、实例/代码版本、最后响应和重复领取保护；本地恢复验证，保留已有对象存储接口 | 按实际拓扑接入持久原件存储，验证进程监管、跨实例状态和重启恢复；不能依赖不可共享的本机文件路径，单机文件心跳不能假装证明多机 Worker 正常。不预建集群调度器 |
| 健康、日志、备份 | 准确区分组件状态，管理记录可查；交付本地启动和恢复步骤 | 部署平台提供故障通知、持久存储备份及实际恢复演练、访问和日志保留配置，不要求自建备份/监控 UI |
| 发布与撤回 | 受控本地权限、一次整体收录、旧版本失效机制验证 | 在实际对外展示范围验证认证隔离、公开 API 字段、撤回缓存与恢复；不能直接放开旧本地 API |

这五项是具体上线环境的必要适配/验证清单，不自动增加为每份内容的审批流程，也不要求先实现它们才完成本地试用。P5 交付部署接口说明、已验证范围和明确未验证项；真正启动上线任务时按所选宿主完成对应工作。未来如出现多人日常分配账号、频繁来源编辑或多实例运营，再以实际频率/规模立项扩展页面，不提前建设。

#### 4.2.7 实施限制与完成判据

系统管理并入原五项任务，不设第六个管理平台项目：P1 提供运行/连接、来源读取、旧历史可达和现有步骤恢复；P2 补来源暂停/恢复；P4 统一变更/使用限制的管理说明；P5 验证四个入口、旧路线退出及部署边界。

P1 的首要出口仍是“一次收录后总览可读”。管理部分先迁移现成能力，只补退出旧控制台所必需的缺口；不得先写监控、账号中心或来源编辑器再开始收录闭环。

以下全部成立才把最小管理模块标为已实现：操作员能在新入口完成必要维护；审核员不需进入管理页也能完成正常和带备注收录；直调 API 无法越权；WMA 离线不使历史总览消失；旧公告理解路线不再被入口或启动器带回；功能和状态来自实际持久数据。管理模块本地完成与生产适配完成分别记录。

新增定向验证范围：`backend/tests/api/test_system_management.py`（读取/维护/收录权限不混用、秘密不泄露、状态查询局部失败）、`backend/tests/integration/test_management_actions.py`（来源暂停与失信分离、恢复幂等、配置修订和会话撤销）、`web/tests/system-management.test.tsx`；在 P5 的隔离浏览器配置中增加 `web/e2e/system-management.spec.ts`，覆盖四入口、无权限直访、旧深链及 WMA 离线时仍可完成现有内容审核。禁止拿生产配置或真实数据跑清表测试。

## 5. 分五个实施任务交付

所有 P 项当前均为未实现。本轮完成的是路线取代及文档，不用文档数量、迁移数量或测试数量估算业务完成度。按 P1 → P2 → P3 → P4 → P5 集成；不先补齐全部后台治理再提供体验。

### P1：先打通“一次决定后真的进入总览”

## 7. 验证、迁移与回退规则

- 每个 P 项先建立代表性失败样例，再实现与运行定向验证。计划内新增测试路径在创建后执行，不把计划命令当成实际通过。
- 后端使用 `uv run python -m pytest`、Ruff、mypy 的受影响范围；数据库/权限/版本改动补集成验证。前端执行相应测试、类型检查和生产构建，并用隔离 Playwright 验证真实页面操作。
- **集成测试会清表。** 执行前核对宿主、容器、端口、数据库及用途；已知隔离库使用 55437，真人库为 55439，不能仅凭环境变量名判定安全，更不能在 55439 运行集成测试。
- 本地试用切换前备份数据并验证恢复材料，核对 API/Web/Worker 实际版本。当前已有 0056–0066 文件不代表真人库已升级；执行时以实时迁移状态为准。
- 迁移追加而不覆盖历史。跨工作树同名模块或迁移先比较，原附件所在 0e97 工作树本轮只作为资料来源，不自动合并其代码。
- 同一输入、代码和环境的有效证据可复用；新缺陷或接口改动才扩大回归。文档变更不要求跑全部程序测试。
