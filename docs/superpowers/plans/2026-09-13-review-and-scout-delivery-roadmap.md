目标：先让审核员连续完成一份真实公告中两个岗位的核对，再让外部来源研究包得到真实接收回执，最终把经审事实与资格接入用户行动链路。

工具链：Python 3.14、FastAPI/SQLAlchemy/PostgreSQL、Node 24、Next/React、Corepack 固定 pnpm 10.15.0。测试与真人数据使用不同数据库。

执行方式：按下面的可交付切片顺序推进。日常技术选择沿用当前会话授权与 AGENTS；不照搬参考包的逐项重新批准、固定三轮停止、强制新工作树或禁止合并模板。真人责任决定仍由有权人员本人完成。计划形成后已收到继续实施委托，按切片持续执行；尚无实现证据的后续项仍为计划。

包检查无外部请求、不执行包内代码：阻止穿越、绝对/危险路径、符号链接、重复成员、CRC 错误、加密及展开超额。参考的 100 MiB 上传、500 MiB 累计展开、50 MiB 单成员、10000 成员、嵌套两层是初始拟议限额，落地前与真实包实测对齐。流式累计真实读出字节，不只信头部大小。

保存原包和全部可读观察，规范化值与修复建议单独版本化。来源角色、权威、优先级分离；无来源核验不升权。绝对路径不得在本机跟随打开；附件唯一哈希匹配仅生成别名建议。两处大小声明差异保留“声明/实测”，不据此擅称文件损坏。

事务内保存选择集及回执记录，提交成功后才返回成功。回执至少绑定包与规范化版本、逐候选命名空间/批次/版本、接收/拒绝/待补及原因、内部接收对象 ID、服务端主体、提交时间和持久回执 ID。事务 ID 使用持久业务提交标识，不把 PostgreSQL 易回绕的底层事务号当长期唯一证据。

首版采用经过身份验证的主系统回执查询核实发行方；离线导出的 JSON 若没有可信签名，仅显示结构/绑定已检查，不能显示“发行方已确认”。签名验证只在确有离线验证需求时追加，避免先建完整 PKI。

退出用例：同包再提交得到同一接收结果；同 namespace/run 不同内容显式冲突；请求键同键异体冲突；事务回滚不返回成功；无权限者不能接收或读取他人对象；正式来源/机会表不变，WMA 调用为 0。用户完成一次“导出→上传→接收→工具读取真实反馈”才称接通。

## 7. CI 与开发成本

当前 `.github/workflows/ci.yml` 已集中 Web 通用检查、完整集成测试和构建复用，仍保留九个 job；选择性测试尚未实现。过去的去重结果见 [CI 去重记录](../../development/2026-09-11-ci-deduplication.md)。本轮未重新统计远程运行时长和账单，不引用旧单次时长作为当前均值。

1. 在 R1 各交付中收集 job/test 时长、关键路径、失败/重跑次数和变更模块；区分墙钟等待与 Actions 资源时长。
2. 先让测试选择器只输出建议、实际仍跑完整回归，积累至少 10 个相关 PR 的对照；这只是拟议观察窗口，不保证统计充分。
3. 低风险且依赖明确的文案/独立 UI/模块变更使用最小相关集合；资格内核、共享契约、鉴权、迁移、依赖锁文件、CI 自身和未知分类完整回归。一行鉴权修改也可能是高风险，PR 行数不作为规则。
4. 主线与发布候选保留完整回归；周期全量如需自动运行，另按明确调度请求配置。检测到选择漏测立即回退全量并修依赖映射。
5. 暂不以 skipped 冒充“九项全绿”。在必需检查契约正式变更前，继续既有同一准确候选九项成功、合并预览同树、合并结果同树的验收方式。

因此“小 PR→小测试集，大 PR→完整回归”的担心成立，但落地规则应是“影响范围与风险→测试集合”。优化先有测量和漏测保护，再减少等待，不能先删保护性测试。
