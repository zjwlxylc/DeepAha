# DeepAha Phase 0 工程基础设计

> 状态：`PROPOSED`  
> 日期：2026-08-21  
> 对应路线：`docs/development/system-roadmap.md` 的 Phase 0

## 1. 背景

DeepAha 将逐步形成机会采集、文档理解、机会版本、资格规则、用户匹配、反馈评估和可信发布能力。当前工作区只有产品文档、设计参考与协作约束，还没有可执行代码、依赖锁、测试或持续集成。

Phase 0 的任务是建立一个足够小但可持续扩展的工程底座，让后续每个阶段都能以纵向切片（vertical slice）交付，并用同一套本地与 CI 证据验证。

## 2. 目标与成功标准

### 2.1 目标

- 建立单仓库（monorepo）目录与清晰模块边界。
- 建立 Python/FastAPI 后端最小应用，提供存活、就绪和版本接口。
- 建立 Next.js Web 最小应用，展示正式文字品牌和系统定位。
- 建立后端与前端的静态检查、类型检查、测试和生产构建。
- 建立根目录统一验证入口和 GitHub Actions CI。
- 给新开发者提供从零启动、验证和故障定位说明。

### 2.2 可验证成功标准

在全新检出环境中：

1. `backend` 能按锁文件安装，健康与版本契约测试通过。
2. `web` 能按锁文件安装，Lint、类型、组件测试和生产构建通过。
3. `scripts/verify.ps1` 能一次执行 Phase 0 的全部本地质量检查。
4. CI 使用与本地一致的命令，两个运行时作业均通过。
5. 页面只使用经确认的文字品牌；不直接使用带底色或水印的原始 `设计/logo.png`。
6. 仓库中没有真实秘密、业务占位实现或伪造的完成指标。

## 3. 范围

### 3.1 包含

- 根目录工程文件：`README.md`、`.gitignore`、`.editorconfig`。
- 后端：应用工厂、配置、结构化 JSON 日志、请求 ID、健康与版本端点。
- Web：App Router、全局样式、可访问的最小首页、基础元数据。
- 自动化：后端测试、前端组件测试、根验证脚本、CI。
- 开发说明：环境要求、安装、启动、验证、目录说明。

### 3.2 明确排除

- PostgreSQL、数据库迁移、缓存、队列和对象存储。
- 采集器、网页解析、OCR、实体归并与机会入库。
- LLM 或任何外部模型调用。
- 规则引擎、用户画像、匹配、推荐和通知。
- 登录、权限、管理后台和真实业务页面。
- 部署生产环境、域名、云资源和监控平台接入。
- 正式图标的清底、矢量化或重新绘制；该工作另立视觉资产任务。

## 4. 架构决策

### 4.1 仓库结构

```text
DeepAha/
├── backend/
│   ├── src/deepaha/
│   │   ├── api/
│   │   └── core/
│   └── tests/
├── web/
│   ├── app/
│   └── tests/
├── scripts/
├── docs/
├── 文档/
└── 设计/
```

采用模块化单体（modular monolith）：后续领域能力仍在一个后端部署单元中，但按 `sources`、`documents`、`opportunities`、`rules`、`matching`、`evaluation` 等模块保持所有权边界。Phase 0 只创建 `api` 与 `core`，不预建空业务模块。

### 4.2 后端

- Python `3.14.x`，由 `.python-version` 固定大版本。
- `uv` 管理项目、虚拟环境与锁文件。
- FastAPI 提供 ASGI 应用和 OpenAPI。
- Pydantic Settings 读取环境配置；配置前缀为 `DEEPAHA_`。
- 标准库 `logging` 输出单行 JSON，避免 Phase 0 引入额外日志框架。
- 每个请求读取或生成 `X-Request-ID`，写入响应头和请求日志。
- `GET /api/v1/health/live` 只证明进程可响应。
- `GET /api/v1/health/ready` 在无外部依赖的 Phase 0 返回就绪。
- `GET /api/v1/version` 返回应用名、应用版本、API 版本和契约版本。

### 4.3 Web

- Node.js `24.x LTS`、Corepack、pnpm 锁文件。
- Next.js `16.2.x LTS`、React `19.2`、TypeScript strict。
- 首页是服务端组件，仅展示 DeepAha 定位和“正在建立可信机会基础设施”的状态。
- 样式以 `设计/logo.png` 的深蓝、亮蓝、橙色和灯塔意象为视觉参考，但不嵌入原始图片。
- 不添加表单、仪表盘、假数据、假导航或尚不存在的功能入口。

### 4.4 本地验证与 CI

根脚本按顺序执行：

1. 后端格式检查、Lint、类型检查、测试。
2. Web Lint、类型检查、组件测试、生产构建。

CI 拆为 `backend-quality` 和 `web-quality` 两个独立作业，以便快速定位失败。依赖只能按锁文件安装。

## 5. 接口契约

### 5.1 健康响应

```json
{
  "status": "ok"
}
```

`live` 与 `ready` 在 Phase 0 共享响应模式，但保留不同端点语义，后续 `ready` 才加入数据库等依赖检查。

### 5.2 版本响应

```json
{
  "app": "deepaha-api",
  "version": "0.1.0",
  "api_version": "v1",
  "contract_version": "0.1.0"
}
```

字段变化需要更新契约测试。提交哈希或构建时间等部署元数据不在 Phase 0 强制范围内。

## 6. 错误处理与日志

- 未捕获异常由框架转换为 500，正式响应不暴露堆栈和配置。
- 请求日志至少包含 `timestamp`、`level`、`event`、`method`、`path`、`status_code`、`duration_ms`、`request_id`。
- 健康端点不打印请求体；Phase 0 的所有端点均无用户敏感数据。
- 配置错误应在启动时失败，不以静默默认隐藏错误。

## 7. 测试策略

后端测试：

- 三个端点的状态码与响应体契约。
- 传入 `X-Request-ID` 时原样返回；未传入时生成非空值。
- 设置对象默认值和环境变量覆盖。

前端测试：

- 首页包含 `DeepAha`、`Go Deep. Find the Aha.` 和中文定位。
- 主标题结构可被辅助技术识别。
- 不测试框架内部实现或 CSS 像素值。

构建验证：

- 后端由类型、导入和测试覆盖启动路径。
- Web 必须通过 `next build`，捕获服务端/客户端边界和类型错误。

## 8. 安全与隐私

- `.env*` 默认忽略，仅允许提交 `.env.example`。
- 不提供任何默认外部令牌、数据库地址或分析脚本。
- 响应头中的请求 ID 只接受受限长度的可打印值；异常值重新生成。
- 依赖安装使用锁文件；CI 不执行来源不明的脚本。

## 9. 品牌与可访问性

- 正式文字：`DeepAha`。
- 正式标语：`Go Deep. Find the Aha.`。
- 中文定位：帮助青年把分散、变化、复杂的机会信息转化为可理解、可判断、可行动的路径。
- 色彩需满足正文和交互文本的 WCAG 2.2 AA 对比度。
- 页面必须支持键盘和减少动画偏好；Phase 0 不引入非必要动画。
- `设计/logo.png` 是品牌语义基线，但其白底/水印未处理前不得作为生产资产。

## 10. 风险与控制

| 风险 | 控制 |
|---|---|
| 过早搭建完整平台 | Phase 0 只创建实际使用的目录和端点 |
| 版本过新带来生态不兼容 | 固定大版本与锁文件，CI 验证安装和构建 |
| 本地与 CI 命令漂移 | CI 调用与根验证脚本相同的子命令 |
| 原始视觉文件被误当成生产资产 | 首页只实现文字品牌与色彩语言 |
| 文档先于实现产生虚假状态 | 本文标注设计状态，Gate 证据另行生成 |

## 11. Phase 0 出口 Gate

- 所有成功标准有实际命令输出支持。
- 后端和 Web 在全新环境按文档可复现。
- CI 在默认分支保护前已通过。
- 目录没有空业务模块和未来功能占位代码。
- `docs/gates/phase-0/` 保存实际验收、测试和延期事项。
- Phase 1 只能在 Phase 0 Gate 关闭后开始。
