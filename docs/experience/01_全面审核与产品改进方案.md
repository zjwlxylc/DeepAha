## 一、结论：继续产品化，不再另起一套系统

当前系统已经不只是“抓公告、做展示”的原型。代码中可以辨认出来源登记与 Scout 接收、Direct WMA 调查、不可变原件与候选内容、一次整体审核、具体岗位或赛道级收录、资格与价值分开判断、收藏与申请进展、消息与反馈、实验室、邀请准入及运维底座。它们有对应的前端、接口或业务实现，不应该再次被规划成“将来从零补齐的功能”。[S01、S04–S15]

本次建议是：**保留已经形成的业务边界，重新组织信息和操作路径；对确实限制使用的少数接口做小范围扩展。** 不建议重建数据库、不建议重做一套审核引擎、不建议为了换界面强制迁移 React/Next.js，也不建议把本地资格规则重新交给大模型随意决定。

目前更合适的成熟度判断是：“业务闭环与试运行底座已经成形；真实用户完成任务的效率、来源规模扩大后的操作体验、受控并发及持续价值仍需验证。”不能据仓库的测试数量就认定推荐效果、商业转化或大规模稳定性已经得到证明。

## 三、从第一性原理重新确定产品重心

### 1. 用户真正要完成的任务

不是“看更多信息”，而是在有限时间内回答五个问题：这条机会是否真实且仍有效；是否与我有关；我能否参加；是否值得投入；下一步具体做什么。

据此，把产品价值拆成一条可观察的链：

**当前有效的官方材料 → 值得看的具体机会 → 可解释的资格判断 → 可执行的一步 → 真实行动与结果。**

任何一环失效，扩大前一环的数量都可能只会放大噪声。增加来源数不能替代内容更新可靠性；提高模型调用量不能替代附件读取质量；增加卡片不能替代“知道下一步该做什么”。

### 2. 三种角色，三种成本

普通用户的成本是注意力与准备时间；审核员的成本是理解一份返回并作整体决定；维护员的成本是定位生产链中断在哪里、怎样继续且不重复付费。三者需要不同的页面，不应共用一套堆满技术字段的“万能工作台”。

### 3. 四个不变的原则

**公开信息不人为设障。** 公开总览提供可用的官方机会，不靠隐藏报名条件制造付费压力。后续持续价值来自省时、更新提醒和行动支持，而不是防止用户“免费找到机会”。支付本轮不新增。

**资格不是推荐分数。** “很值得看”不能推导为“有资格参加”；“证据不足”也不能直接推导为“不符合”。内部排序分数不包装成精确匹配率。当前 `value.py` 已明确采用本地可解释排序，内部数值不属于公开结果契约；这条路线值得保留。[S16]

**不确定性要具体。** 把“系统有风险”改为“尚未填写团队人数”“截止时间在两份材料中冲突”。需要用户行动的风险默认可见，原件与长说明按需展开。

**一项操作只承担一种授权。** 接收 Scout 资产不是批准采集；批准来源不是立即调查；结果接收不是公开收录；公开收录不是批准个人资格；恢复文件不是重新调用模型。

## 五、关键发现与优先级

### F01｜画像渐进补充存在真实接入陷阱：必须先修接口使用方式（P0）

**事实：** `PersonalMixin.set_profile()` 最终执行 `p.data=cleaned`，当前 PUT 是整份替换，不是局部合并。[S12]

**影响：** 新 UI 从详情点“补充团队人数”，若直接 PUT 一个 `team_size`，会丢掉城市、证书、通知等未提交字段。这不是当前所有页面都已经丢数据的结论，而是改造时必须防止的可定位风险。

**方案：** 第一阶段维持完整表单对象，保留页面未呈现的字段，并在保存前合并；跨标签页仍可能最后写入覆盖，因此随后增加版本化 PATCH 或 ETag/If-Match。显式空值代表用户清空，字段缺席代表不修改。测试覆盖生日清空、通知偏好保留、隐含证书字段和并发编辑。

### F02｜新建调查的来源选择只拿默认第一页（P1）

**事实：** 当前前端 `newTask()` 请求 `/api/manage/sources`，再在客户端筛选启用项；API 默认上限 50，来源列表本身虽然分页，新建任务选择器没有持续读取分页。[S06、S04]

**影响：** 来源超过 50 个后，后面来源可能无法从这个选择器中选到；前 50 个全暂停时，还可能误以为没有可采集来源。

**方案：** 增加服务端搜索选择器或完整分页读取；选中的具体来源需再次按当前授权状态校验。不要靠一次请求改成几千条掩盖问题。测试至少 120 个来源、目标在第 3 页、选中后被暂停三种情形。

### F03｜WMA 并发不是增加一个 UI 数字框（P0 设计边界，P2 实施）

**事实：** 当前 `ConnectionConfig` 是单一 Agent 配置；worker 的 `run_once()` 每次选取一个任务，使用单一心跳条目，没有读取并发策略或模型级配额。[S09、S10、S13]

**不作出的推断：** 没有实测供应商并行能力；没有证明现有数据库事务在多 worker 下已经安全；不声称 AGENS 官方只允许一个线程。

**方案：** 先保持串行与现有单连接可用。将连接绑定、能力验证、执行策略、调度实施分成四层。AGENS 按用户确定的项目策略锁定为 1；未知模型或未知发布绑定也保守为 1；其他连接只有通过真实验证后才允许受控并发。需要原子领取/租约、连接级并发上限、队列容量、预算、暂停、审计、回退和回收专用状态机。

接口目前没有 `model_id`、`max_parallel` 之类的生产契约。不得仅把拟议字段加进网页并宣称模型配置已生效。连接的实际模型或能力应从可信发布绑定读取；若供应商不能在每次请求中切换模型，应配置不同已发布 Agent/连接，而非伪造请求参数。

### F04｜任务有正确边界，但仍偏“记录表”而非“处理工作台”（P1）

**事实：** 已有阶段翻译、人工刷新、回收恢复、停止后续处理和警告；并非完全没有任务管理。列表缺少面向当前任务全集的状态/来源搜索，详情主要是标识、预算、次数和会话。[S06、S13]

**方案：** 将“等待调查、调查中、待回收、配置变化、结果已接收”分栏统计；每条任务给出人类可读的原因与唯一建议动作。待回收用“继续回收已有文件”；来源变更用“按新配置另建调查”；已接收用“打开审核”，而不是一概“重试”。后台展示时间预算，不把秒数标成金额。

### F05｜审核应减少视觉负担，不减少事实或防冲突检查（P1）

**事实：** `intake.py` 已保留原始 ZIP、解析失败后的原件、整体备注、预览 hash、幂等键、已有决定与来源版本检查。普通备注与 `can_approve` 是不同层次。[S17]

**方案：** 默认看接近用户端的收录预览；原件、变更、备注三类信息分组；展示父公告数、具体机会数、受影响范围。一般备注可随结果收录，不能变成“逐字段打勾”。硬阻断仍由后端决定，前端不能设置“忽略全部检查”。

审核附言在现有返回中是 `overall_note`；不能假设它自然成为用户可见的公开说明。需要公开编辑说明时，应单独设计字段、权限、审计与展示契约，本轮不借整体审核暗中增加编辑事实的权力。

### F06｜首页和详情应落实最近约定，而不是再加说明层（P1）

**事实：** 最新文案清理确实已减少大量用户端解释；但当前 `marketingHome()` 仍包含流程、判断示例、行动示例等中间段落，还含固定日期的示例内容。[S03、S05]

**方案：** 原型落实首屏＋品牌收束两段结构，不恢复第 2–4 段长解释；总览和个性化入口同层清楚可见。静态示例要明确标识，正式计数与时间只从真实数据读取。原型对最终两个按钮实测 hover 文字对比度为 7.52:1 与 15.54:1；这是本原型结果，不是生产页面测试结论。

### F07｜当前排序是透明规则，应该迭代验证，不包装成更强的 AI（P1 持续验证）

`value.py` 用机会类型、地区、方向、兴趣、技能等显式信息做召回与排序，采用有限词汇提示，不调用 LLM。高风险不确定资格有独立推荐闸门，不能挤占重点展示。[S16]

优点是低成本、可解释、可复现；限制是表达变化、跨领域兴趣和长尾机会可能覆盖不足。下一步应先建立“用户为什么觉得不相关”的反馈分类与分层样本，再比较当前规则与新增检索方案。不能先把语义模型接上去，再用自身排序结果作为标准答案。

### F08｜手机后台应先支持查看与分流，不一次开放全部危险操作（P1）

当前工作台在手机上直接引导去电脑。[S06] 新原型允许查看来源状态、任务详情、待审核内容；但整体发布、来源授权、任务新建、策略和账号修改仍限制桌面。这样先满足临时查看需要，不扩大未验证的移动操作风险。正式业务是否允许移动审核应独立验收，不因 CSS 能显示就默认开放。

### F09｜已有安全基础，不能把“检查未覆盖”写成“没有安全措施”（P0 验证）

代码已存在 scrypt 密码散列、常量时间比对、会话有效期、活动账号复核、CSRF、同源与可信主机检查。登录按 IP 与用户名组合限制失败尝试：15 分钟窗口、达到 8 次后拒绝。[S04、S18]

四字符密码、四位邀请码是当前明确产品设定。[S02] 本轮不暗中修改。但仍需对多 IP 尝试、邀请猜测、用户名枚举、重置、并发最后维护员保护和部署代理 IP 传递做独立测试；已读登录限制不能代表所有入口都已经充分防护。是否提高强度应作为单独产品决策，不能由视觉改造顺手变更。

### F10｜测试与用户效果必须分账（P0 表达，P2 运营）

正式回执、单元测试、合成浏览器数据、数字分身、独立人工标注与真实用户反馈是不同证据。实验室界面必须显示样本来源与分母。原型中的“运行检查”只运行本地演示约束，不是原仓库 SG7 基准，也不产生真实推荐准确率。

## 六、各模块的最终体验定义

### A. 发现与判断

首页先让用户选择“公开看机会”或“进入我的星图”。总览以具体可行动对象为卡片主体，分类用统一词典；父公告负责共同内容，避免多个岗位卡片重复整篇公告。详情首屏依次是标题与组织、时间、资格状态、核心条件与行动入口。长引用保留为按需展开，不把真正影响申请的时间冲突藏进折叠区。

星图默认使用少量重点机会＋探索列表，给出一句个人相关理由。不设用户看不懂的雷达图或匹配百分比；可选星图视图只是导航方式。缺少画像时应列出最能改善判断的一项，而不是一开始让用户填完所有字段。任何补充都需明确用途，并保留不填、关闭个性化、导出与清除能力。

### B. 行动与持续使用

行动从一条具体机会开始，保留“已收藏、准备中、已申请、等待结果、已完成、暂不考虑”语义。看板只是这些已有状态的另一种视图；按钮和选择器提供不依赖拖拽的操作。

准备清单、个人备注和下一步属于用户工作区，不能被当成官方新增要求；拟新增的个人清单需独立保存。消息按截止、变化、周摘要分组，只发送有具体意义的信息。一次机会完成后允许进入低频关注，而不是为了订阅数据强迫用户每天回来。

### C. 内容生产与审核

来源页面回答“这个入口是否授权、是否健康、下一次做什么”；来源资产页面回答“本次研究包带来了哪些新候选、重复项和缺口”。调查任务页面回答“是否已发给远端、卡在哪里、哪种恢复安全”。审核页面回答“将公开什么、哪些问题随内容保留、是否允许作整体决定”。四者互相跳转但不混成一个表。

### D. 质量与系统

运行概况区分数据库读取、原件读写、worker 响应和 Agent 发布绑定，不把“已保存密钥”显示成“调用已成功”。账号页直接写出用户、审核员、维护员的权限继承；最后有效维护员保护仍由后端保证。实验室提供来源可辨认的失败样本与运行记录，不能自动回写生产规则或审批决定。

## 七、落地顺序与验收

**第一批：安全接入与已有功能体验。** 固定最新基线与截图；避免画像覆盖；统一导航、卡片、状态、首页两段、详情、审核预览与操作文案；保留现有 API、权限、CSP、证据和数据。验收重点是“改界面不改资格/审批含义”。

**第二批：规模化操作小补强。** 来源服务端搜索、任务筛选和阶段详情、画像版本化局部更新、必要的行动清单持久化。必须先明确 DTO 和兼容策略，再接界面。不能用当前页计数冒充数据库总计。

**第三批：调度与真实效果。** 在隔离环境验证连接能力、原子任务领取、受控并发与失败恢复；只对经过批准的其他连接开放。并行上线与 UI 上线分开回退。同时开展小规模真实任务可用性观察，不用原型结果代替产品成绩。

每批以一个独立可验收成果为单位，单任务窗口推进；自修复最多三轮，仍失败就停止并提供最小复现。未经人工验收不合并、不切正式站。详细执行与接口计划见后两份文档。

## 八、建议追踪的真实指标

不以模型调用数和采集条数作为成功指标。建议观测四组有明确分母的数据：

1. **用户完成任务：** 在已查看机会的用户中，能说明资格风险、找到官方入口、完成下一步的人数比例；分别记录新用户与已有画像用户。
2. **内容可靠性：** 已收录具体机会中，关键截止明确且当前有效的比例；已发现变化从回收到展示的时间；失效提醒与误报分别计数。
3. **运营效率：** 一份返回从进入审核到整体决定的时间；每次调查产生的可收录具体机会；重复调用、待回收及人工补查占比。
4. **真实价值：** 用户自述此前是否知道、是否有用、是否实际准备/申请及结果；自愿反馈与沉默用户不能混在同一分母中。

先建立基线再谈提升，不预先承诺 90% 命中率、具体订阅转化或留存增幅。机会需求本就有阶段性，完成一次申请后暂时不用不应自动被视为产品失败。
