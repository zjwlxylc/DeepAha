# 宿主放行与回退清单

**本轮未发布。不能凭自动测试 PASS 直接执行旧 deploy_public.py。**原正式站服务在历史记录中命名为 staging/8100，隔离 staging 为 staging-isolated/8200；发布时先重新核验实际拓扑，不根据名称猜环境。

## 推荐顺序

1. 在新目录解压并核对文件哈希；不要在线改 production 源码，不动本次范围外 Gateway/Nginx。
2. 关闭新调度，查清在途/状态不明远端任务；停止 API/Worker，阻止其他写入。
3. 正式数据库与对象同时备份；PostgreSQL 必须在独立空目标实做恢复演练。
4. 对隔离环境执行 `upgrade-experience`，复核旧表行数、账号密码散列、旧审核/公开数据不变；跑本包全部测试及 PG 并发验收。
5. 验证真实 HTTPS/Cookie/CSRF/角色、手机浏览、画像冲突、清单和审核，按 D1 做真人任务。
6. 维持串行可先验收界面；真实 WMA 并发是另一道门，不与界面放行混成一个按钮。
7. 人工明确批准后，才进行生产切换、Smoke 和回执归档；不得覆盖当前库回放测试数据。

## 回退不能只切回旧 Worker

新增表可以保留，**但旧84353c7 Worker不认识命名连接、任务快照、租约和实测占用**。因此不能在新库中有排队/回收/远端不明任务时，把 Worker 直接换成旧版并启动；它可能拿错任务或绕过调度上限。最低风险回退是停止 Worker，先只回退只读服务/界面；若必须回退整套服务，需要先逐一关闭或隔离新任务并核实远端结束，负责人审批后再启动旧 Worker。

新旧 API 与前端必须同步切换；不能让新画像 PATCH UI 接旧 API。旧 PUT 版本的服务也不会维护新增画像修订号。重新回到新版前，必须停止写入，撤销旧会话、关闭所有旧标签页，并在宿主事务中推进全部 `product_profile_revisions.version`，防止旧版本号复用导致迟到草稿覆盖。此步骤需另行核验，不由本包自动在回退时改库。

**禁止把备份直接覆盖恢复到仍接受写入的当前数据库。**需要恢复时先在新数据库/新对象目录恢复验证，再按独立恢复流程切换，避免丢掉备份后的用户记录。
