# GROUP 规则对岗位的适用决定持久化

范围为内部后端服务与迁移 0049：独立保存 `APPLIES`、`DOES_NOT_APPLY`、`NEEDS_ADJUDICATION`。本批内部实现 IMPLEMENTED，本地定向验证通过，精确候选 CI 待检查。没有新增 API、表单、继承计划或资格放行；原只读页面仍显示尚未裁决，待后续专门接入决定服务。

每条决定绑定当前任务、官方材料包、组成员、组事实与规则审批、岗位版本和已保存岗位计划。明确适用或不适用必须提供官方段落中的精确引文；待裁决允许无引用。保存后记录原始请求、上下文、证据定位与摘要。更正采用追加记录及前序比较，同键同请求返回原回执，不同请求冲突；任务行锁串行化并发提交。写前、写后和读取均重新核对权限与实际上下文。

数据库禁止修改和删除记录，重建真实组审核并校验完整上下文、JSON 类型、枚举、必需字段、精确引文和实际定位。对伪造内容重新计算摘要也不能绕过校验。空表允许迁移回退；已有历史时拒绝回退，防止删除审计记录。

同组其他规则后续批准会改变完整审核摘要。历史读取只接受实际不可变审核历史的精确前缀，并检查其时间不晚于适用决定；原记录与摘要不改写。迁移在同一任务行锁内要求后续组审核的 `(created_at, decision_id)` 严格递增，防止回填时间或同时间倒序插入破坏已有前缀。新增更正必须绑定当前完整上下文。上下文变化后的旧请求重试会返回上下文冲突，调用方应刷新并用新的请求键和当前前序提交，不能把旧摘要作为当前状态。

独立审阅指出的三个问题已实施修复：数据库未重建审批摘要、JSON 校验与 Python 契约不一致、同组新增批准使旧记录不可读。复审补出的 SQL 时区格式与历史回填问题也已修复，静态复核无剩余 P1/P2。

验证：首轮相关 PostgreSQL 103 项通过（新决定 30、组事实 32、只读适用上下文 15、组规则审核 26）。最后补强迁移后，重跑受影响的新决定 32 + 组规则审核 26，共 58 项通过，0 失败、0 错误、0 跳过；包含 0049 空表降级/升级及 Alembic 模型一致性、有历史拒绝降级、双连接幂等和前序竞争、来源政策变化回滚、重新哈希伪造拒绝、历史不可改写、兄弟审核追加与回填拒绝、两时区 SQL 摘要及写入。5 文件 Ruff 与格式检查、决定服务 mypy 通过。无前端改动，未重复整站测试或生产构建。

证据：`evidence/2026-09-10-group-applicability-decisions-{initial,final}.xml`；`evidence/2026-09-10-group-applicability-decisions-validation.json` 保存实际计数与源码 SHA256。首轮样本曾使用两个相同归一字段，导致准备阶段被正确拒绝；改为独立字段后验证目标生命周期。新回填负例在成对审批模型写入处改时间，不禁用数据库约束。

SQL 审核摘要统一使用 UTC，与 Python `Instant` 一致。时区测试仅证明 UTC / Asia/Shanghai 会话下新 SQL 重建摘要相同、合法写入后可由 UTC 服务读回。尝试整套服务切换到非 UTC 时，在既有 `unit_snapshots._checked_view` 就触发 `UNIT_PLAN_INTEGRITY_FAILED`，尚未到新决定写入；这是旧岗位快照的时间表示兼容问题，本批不修改，不能据新 SQL 测试声称整个服务支持任意会话时区。下一 API/UI 批继续使用已经验证的 UTC 数据库会话。
