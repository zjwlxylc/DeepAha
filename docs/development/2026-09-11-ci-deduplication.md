# CI 第一阶段去重

本批保留九个检查名称、所有不同的 pytest 命令、各阶段迁移往返和浏览器场景。目标是减少重复运行资源；不按 PR 行数跳过测试，不改变领域发布门。

| 检查 | 原运行次数 | 本批运行次数 |
| --- | ---: | ---: |
| 完整后端 integration | 2 | 1 |
| Web test / build，各自 | 4 | 1 |
| Web lint / typecheck，各自 | 3 | 1 |
| 后端 Ruff format / check / mypy，各自 | 2 | 1 |

完整集成测试由 integration 承担；phase3 继续跑领域测试和数据库结构检查。phase4–8 保留各自领域回归、数据库迁移及隔离环境。web-quality 负责前端通用检查和调查/关系浏览器场景。

Phase 8 等待 web-quality，通过同次 workflow run、同一 github.sha 的 artifact 复用生产构建，并在自己的数据库与 API 环境运行提醒浏览器场景。构建在 relations 开发服务器运行前归档，避免 .next 被覆盖。依赖仍按锁文件独立安装。artifact 保留一天，不包含构建缓存；完整重跑覆盖同名 artifact，仅重跑失败下游任务仍可读取前一 attempt 的同 SHA 构建。artifact 已过期时须重跑全部任务，不能把下载失败当作验证通过。

同 PR 新提交取消旧运行；main 不启用运行中取消。此设置不承诺每个密集 push 都独立运行，合并验收仍要求准确候选九项成功。Phase 8 新增依赖会推迟它的启动，因此资源减少不等于关键路径同比缩短。

## 基线与验证

基线为 PR #47 CI #149（run 34534646540）：九个 job 的日志首尾时长合计约 49.6 分钟，其中两次完整 integration 所在 job 分别约 17.1 和 17.9 分钟。该数字是日志时长之和，不是账单或严格计费分钟；单次样本也不能代表长期均值。

本地保护测试先得到 3 失败 / 1 通过，实现后新测试 4 项通过；首轮远程运行暴露 Phase 6–8 旧保护测试仍要求阶段内重复前端命令，已将断言转为集中检查 web-quality，并保留阶段隔离和独有验证要求。包括这些既有保护测试在内的 [23 项定向回归通过](evidence/2026-09-11-ci-dedup-unit.xml)，Ruff 和 mypy 检查通过。另以 YAML 解析比较父提交和本批配置，确认九个 job、不同 pytest 命令集合、逐 job 迁移与浏览器命令均保留。跨 job 构建复用的最终证据以本批 PR CI 为准。

## 后续选择性测试（PLANNED）

先积累各测试组时长、失败和重跑数据，再建立模块到测试的依赖映射。只对明确低风险、影响可界定的变更缩小测试集；资格内核、共享契约、迁移、依赖锁文件及 CI 本身改变时保留完整回归，无法分类时默认完整。主线/发布候选保留完整回归，必要时增加定期全量发现映射遗漏。不能仅按 PR 文件数或行数分类，也不能把 skipped 自动当作领域验证成功。
