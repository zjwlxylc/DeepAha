# 邀请与账号管理使用说明

## 维护员
登录后进入 `/manage/invitations` 发码，默认1人/7天。新邀请码为4位数字，前导0必须保留。历史长邀请码按原有效期继续使用。四位码不重新分配，10,000个码用尽时停止生成。明文只显示一次；复制给受邀者后清除显示。生成数量表示独立码数量，每码名额是可注册账号数。使用批次标签区分邀请来源，不填写敏感个人资料。

`/manage/users` 可搜索账号、修改角色/状态、撤销所有会话、签发密码重置码。`operator`（维护员）拥有 `reviewer`（审核员）的全部权限，同时负责来源/采集、邀请码和账号管理。没有单独的账号管理员角色；发码仅产生普通user。不要为使用邀请码而授予审核或维护权限。修改角色/状态后旧会话与未使用的重置码失效。

密码遗忘：先在线下核验请求者身份，管理员签发30分钟一次性重置码，用户进入 `/reset-password` 自行设置新密码。系统不发送邮件，不让管理员获知新密码。重置码丢失时重新签发。

## 受邀用户
访问 `/register`，输入邀请码、账号和4–256字符密码，确认体验说明。普通账号可正常使用机会、收藏、行动和反馈；邀请码注册并不等于同意参加Lab。

“我的 → 账号安全”可修改密码，所有设备会退出。“我的 → 数据与隐私”沿用个人导出与清除功能。停用账号不等于删除数据库记录或备份；如需清除个人数据，请先使用既有清除功能。管理员不会通过用户列表看到画像或自由文本反馈。

## 宿主与回退
本次仅隔离staging：`deepaha-api@staging-isolated` / `deepaha-worker@staging-isolated`，8200，独立数据库及数据目录。保留Nginx Basic Auth；没有Basic Auth凭据的受邀者暂不能访问staging，这是内部验收环境。正式体验用户仍用当前www版本，待人工验收后另行发布。

`DEEPAHA_ALLOW_REGISTRATION=1` 才显示受邀注册；值为0时关闭新注册但不影响已有用户登录。开启本版本也不允许无邀请码注册。

迁移先完成停服备份，再执行 `python -m deepaha.product.cli upgrade-access`。创建缺失的三张准入表，并将历史admin角色迁为operator；保留用户名和密码，撤销相关旧会话与重置码。不重建数据库、不复制生产数据。首次维护员可对已有账号显式执行 `access-operator USERNAME`；新账号用 `user-add --roles user,operator --password-env ...`，口令从进程环境注入而非命令参数。

若回退到独立admin角色的旧代码，先停隔离服务，使用本次新版本的 `Product.restore_access_roles` 恢复备份 `access-roles-rollback.json` 中的角色映射，再切旧代码。方法会核对当前角色，存在并发角色变更时停止，禁止覆盖。回退必须同时恢复旧staging-isolated发布指针和原环境文件（尤其注册开关），避免旧版本开启无邀请码注册。新增表可保留，禁止覆盖恢复现有数据库；如真需数据恢复，只向新建空库恢复并验证后切换连接。备份及凭据留在宿主受限目录，不进源码包。

部署脚本在切换前核对旧指针，发现并发发布即停止；失败时恢复旧指针和配置、重启原本运行的服务。验收包含真实PostgreSQL单码并发注册、账号隔离、密码重置和禁用会话；该测试账号标记SMOKE并停用，不能计作真实用户反馈。

隔离宿主已使用 `worker --isolated-fixture-mode`，该模式保留原有禁止周期调度和远程客户端的行为。部署包必须包含这一CLI契约及空库初始化保护入口，不能仅按最初SG8-A快照覆盖宿主已具备的隔离能力。
